# Image Viewer — 설계 및 개발 계획

작성일: 2026-11-14 · 언어: Rust · 대상: Windows 10/11 x64 (코어는 플랫폼 독립 유지)

## 0. 목표와 우선순위

1. **극도의 속도**: 실행 즉시 표시, 넘김 시 끊김 없음, 일정한 프레임 (GC 없음)
2. **다양한 형식**: JPEG/PNG/WebP/GIF/BMP/TIFF/AVIF/HEIC/JXL/RAW/SVG/ICO 등
3. **간단한 편집**: 회전·뒤집기·자르기·크기 변경·밝기/대비 등 기본 보정, 실행 취소/다시 실행
4. **형식 변환(확장자 변경)**: 다른 이름으로 저장, 일괄 변환, 잘못된 확장자 바로잡기
5. **확장성**: 코덱·편집 연산·명령을 기존 코드 수정 없이 추가할 수 있는 구조

비목표(초기): 레이어 편집, 그리기/텍스트 주석, 동영상, 클라우드 동기화.

### 참고: ImageGlass v10 분석에서 가져온 교훈

- 빠른 디코더(Skia) 우선 → 만능 디코더(Magick) 후순위의 **2단 코덱 구조**
- 원본 디코드 전에 **저해상도 미리보기 먼저 표시** (JPEG IDCT 축소, EXIF/RAW 내장 미리보기)
- **나선형 미리 읽기** (±1, ±2 …), 메모리 예산, 탐색 시 즉시 취소, 키 누르고 있는 동안 미리 읽기 중단
- 8192² 초과 이미지는 **타일 + 밉맵**
- 실제 사고 사례: 캐시 추적 누락으로 3.6GB 누수, 디코드 취소 중 이중 해제 → Rust 소유권 모델과 명확한 캐시 소유 구조로 예방
- ImageGlass는 GPLv3: 구조만 참고, 코드 복사 금지

## 1. 환경 현황 (2026-11-14 확인)

| 항목 | 상태 |
|---|---|
| 프로젝트 폴더 | 비어 있음, git 저장소 아님 |
| Rust (rustup/cargo) | **미설치** |
| MSVC Build Tools | **미설치** (Rust MSVC 타깃 링크에 필요) |
| cmake / nasm / vcpkg | 미설치 → 초기에는 C 의존성 회피 |
| WIC 확장 코덱 | HEIF 1.2.48, HEVC 2.4.45, AV1 2.0.24, RAW 2.5.24, WebP 1.2.31 설치됨 |

결론: 초기 단계는 **순수 Rust 크레이트 + Windows WIC** 조합으로 C 빌드 체인 없이 진행.
libjpeg-turbo, libheif, libjxl 등 C/C++ 의존성은 이후 cargo feature로 선택 추가.

## 2. 전체 구조

```
┌──────────────────────────── iv-win (순수 Win32 + GDI, M6~) ────────────────────────────┐
│  입력 → Keymap → Command ─┬─> Navigator ──> Library(목록·정렬) ──> Prefetcher(나선형) │
│                           ├─> EditSession(EditStack, undo/redo)                        │
│                           └─> Exporter(저장·변환)                                       │
│  raster(CPU 렌더러·보이는 부분만 리샘플) <── DecodeService(작업자 스레드·세대 취소)    │
└────────────────────────────────────────────────────────────────────────────────────────┘
          │                         │                       │
       (raster, view)          iv-pipeline              iv-ops
          │                         │                       │
          └──────────── iv-codec (Codec 트레이트 + Registry) ┘
                                    │
                                 iv-core (ImageBuf, Metadata, Source, Error, CancelToken)

iv-cli : iv-pipeline + iv-ops + iv-codec 재사용 (일괄 변환·벤치마크·테스트용)
```

### Cargo workspace 구성

| 크레이트 | 역할 | UI 의존 |
|---|---|---|
| `iv-core` | 픽셀 버퍼, 메타데이터, 입력 소스, 오류, 취소 토큰 | 없음 |
| `iv-codec` | 코덱 트레이트, 레지스트리, 형식 판별, 내장 코덱(feature별) | 없음 |
| `iv-ops` | 편집 연산, EditStack, 무손실 변환 판정 | 없음 |
| `iv-pipeline` | 폴더 목록·자연 정렬, 디코드 서비스, 캐시, 미리 읽기, 내보내기 | 없음 |
| `iv-win` | 창(Win32), 입력, 명령, 설정, CPU 렌더러(`raster`), 편집 패널·설정 창(기본 컨트롤) | Win32 (렌더러·명령·키맵·설정은 플랫폼 독립) |
| `iv-cli` | `iv convert`, `iv bench`, `iv probe` | 없음 |
| `iv-libjxl` | 코드 없음: build.rs가 libjxl 0.12(`jpegxl-src` 안의 소스)를 CMake + 기본 MSVC 도구 집합으로 빌드해 정적 링크 (`gamut-jxl`의 JPEG XL 인코더용) | 없음 |

UI 없는 크레이트가 핵심 로직 전부를 담아 **CLI·테스트·벤치마크에서 그대로 검증**하는 것이 원칙.

## 3. 핵심 추상화 (확장 지점)

### 3.1 입력 소스 — `Source`

처음부터 "파일"이 아니라 `Source`로 추상화. 이후 압축파일(zip/7z/rar) 내부 이미지, 클립보드, 드래그 데이터가 같은 경로로 들어옴.

```rust
pub enum SourceKind { File(PathBuf), ArchiveEntry { archive: PathBuf, entry: String }, Memory(Arc<[u8]>) }

pub struct Source {
    pub kind: SourceKind,
    pub display_name: String,
    // 앞부분 바이트(형식 판별용)와 전체 바이트 접근은 지연 로딩 (파일은 mmap)
}
```

### 3.2 픽셀 버퍼 — `ImageBuf`

```rust
pub enum PixelFormat { Rgba8, Rgba16, RgbaF16, RgbaF32 }   // 8비트 경로 최적화, HDR/16비트 보존
pub struct ImageBuf {
    pub width: u32, pub height: u32,
    pub format: PixelFormat,
    pub color: ColorInfo,          // sRGB / ICC 프로파일 / 전달 함수(PQ, HLG)
    pub data: Arc<[u8]>,           // 캐시·렌더러·편집이 복사 없이 공유
}
```

### 3.3 코덱 — `Codec`, `Decoder`, `Encoder`

```rust
pub trait Codec: Send + Sync {
    fn info(&self) -> &CodecInfo;                 // id, 이름, 확장자, 디코드/인코드 우선순위, 능력 플래그
    fn sniff(&self, head: &[u8]) -> bool;         // 매직 바이트 판별 (확장자보다 우선)
    fn decoder(&self) -> Option<&dyn Decoder> { None }
    fn encoder(&self) -> Option<&dyn Encoder> { None }
    fn lossless(&self) -> Option<&dyn LosslessTransformer> { None }  // JPEG 무손실 회전/자르기
}

pub trait Decoder: Send + Sync {
    /// 픽셀 디코드 없이 크기·프레임 수·방향·ICC만 읽음 (목록 정렬, 캐시 판단, 미리보기 크기 계산)
    fn probe(&self, src: &Source) -> Result<ImageInfo>;
    /// 저해상도 미리보기: JPEG 축소 디코드, EXIF/RAW 내장 썸네일 등. 없으면 None
    fn preview(&self, src: &Source, max_side: u32, cancel: &CancelToken) -> Result<Option<ImageBuf>>;
    /// 원본 디코드. req에 프레임 번호·목표 크기(축소 디코드)를 담음
    fn decode(&self, src: &Source, req: &DecodeRequest, cancel: &CancelToken) -> Result<Decoded>;
}

pub enum Decoded { Still(ImageBuf), Animated(Box<dyn FrameStream>) }

pub trait Encoder: Send + Sync {
    /// 품질·무손실·속도 등 옵션을 데이터로 선언 → 저장 대화상자와 CLI가 자동 생성
    fn options(&self) -> &[OptionSpec];
    fn accepts(&self, fmt: PixelFormat, has_alpha: bool) -> Acceptance; // 알파/비트 깊이 지원 여부
    fn encode(&self, img: &ImageBuf, meta: &Metadata, opts: &OptionValues, out: &mut dyn Write) -> Result<()>;
}
```

**레지스트리 선택 규칙**
1. 매직 바이트로 형식 판별 → 확장자는 보조 단서 (확장자와 실제 형식이 다르면 "확장자 바로잡기" 제안)
2. 해당 형식을 지원하는 코덱 중 우선순위가 높은 것부터 시도
3. 실패하면 다음 코덱으로 내려감 (최종 보루: WIC)
4. 형식별 승자는 캐시, 코덱 등록/해제 시 무효화

**코덱 추가 방법**: 모듈 하나 작성 → `Codec` 구현 → cargo feature 추가 → 레지스트리에 등록 한 줄.
런타임 플러그인(DLL)은 후순위. 필요 시 `extern "C"` ABI 어댑터가 같은 `Codec` 트레이트를 구현하는 방식으로 추가 (Rust는 안정 ABI가 없으므로 C ABI 경계 필수).

### 3.4 편집 연산 — `Op`, `EditStack`

```rust
#[derive(Clone, Serialize, Deserialize)]
pub enum Op {
    Rotate90(Turns), FlipH, FlipV,                 // 직교 변환: JPEG 무손실 경로 후보
    Crop(Rect),                                    // MCU 경계 정렬 시 무손실 후보
    Resize { w: u32, h: u32, filter: Filter },
    Adjust { brightness: f32, contrast: f32, saturation: f32, gamma: f32 },
    AutoOrient,                                    // EXIF 방향 적용
    // 확장: 새 변형 + apply 구현 추가. 런타임 플러그인용 Custom(Arc<dyn Operation>)는 이후
}

pub struct EditStack { ops: Vec<Op>, cursor: usize }  // undo = cursor-1, redo = cursor+1
```

- **비파괴 편집**: 원본 버퍼는 그대로 두고 연산 목록만 쌓음
- **화면 미리보기**는 화면 해상도로 축소한 버퍼에 연산 적용 → 큰 사진도 즉시 반응
- **저장 시**에만 원본 해상도로 연산 적용
- 직교 변환/자르기는 가능하면 **GPU 변환 행렬**로 표시만 바꾸고 픽셀 계산은 저장 시점으로 미룸

### 3.5 내보내기 — `Exporter` (저장·형식 변환의 단일 경로)

GUI의 저장/다른 이름으로 저장, 일괄 변환, `iv convert`가 모두 같은 함수를 사용.

```
export(source, edits, target_codec, options, dest):
  1. 무손실 경로 판정: 원본 JPEG → 대상 JPEG, 연산이 직교 변환(+MCU 정렬 자르기)뿐
     → LosslessTransformer 사용 (재압축 없음)
  2. 일반 경로: 원본 해상도 디코드 → 연산 적용 → 대상 형식에 맞게 변환
       - 알파 → JPEG: 배경색과 합성
       - 16비트/HDR → 8비트 형식: 톤매핑 + 디더링
       - 애니메이션 → 정지 형식: 현재 프레임 또는 거부(명시적 선택)
     → 인코드
  3. 메타데이터 정책: EXIF/ICC/XMP 유지(옵션), 방향 태그=1로 재설정, 크기 갱신, 내장 썸네일 제거. 유지하지 않을 때(`--no-metadata`)는 JPEG 무손실 회전도 디코드에 필요 없는 부분(EXIF·XMP·ICC·IPTC 등 APP 세그먼트, 주석, EOI 뒤에 붙은 데이터)을 모두 빼고 방향 태그 하나만 든 EXIF를 새로 씀 (압축 데이터는 그대로, JFIF·Adobe 세그먼트는 유지)
  4. 안전한 쓰기: 같은 폴더 임시 파일에 쓰기 → flush/sync → 원자적 교체(rename/ReplaceFileW)
     → 실패 시 원본 무손상 보장, 덮어쓰기 전 확인
```

"확장자 변경"의 두 가지 의미를 모두 지원:
- **형식 변환**: PNG → WebP 등 실제 재인코딩 (위 경로)
- **확장자 바로잡기**: 내용은 WebP인데 이름이 `.jpg`인 경우 재인코딩 없이 이름만 변경

### 3.6 명령 시스템 — `Command`

모든 동작(다음/이전, 확대, 회전, 자르기, 저장, 변환, 휴지통 삭제 …)을 문자열 id를 가진 명령으로 정의.
키 설정(TOML), 메뉴, 툴바, 이후 스크립트/플러그인이 모두 같은 명령을 호출 → 기능 추가 시 UI 배선 최소화.

```toml
# keymap.toml
"Right"      = "nav.next"
"Left"       = "nav.prev"
"Ctrl+R"     = "edit.rotate_cw"
"Ctrl+S"     = "file.save"
"Ctrl+Shift+S" = "file.save_as"
```

## 4. 속도 설계

| 단계 | 기법 |
|---|---|
| 실행 | 단일 네이티브 exe, 창 먼저 띄우고 디코드는 병렬 시작, 설정 로드는 최소화 |
| 첫 표시 | `preview()`로 저해상도 먼저 → 원본 완료 시 교체 |
| 디코드 | 형식별 최속 디코더 (zune-jpeg 등), 화면보다 훨씬 큰 JPEG는 축소 디코드 |
| 넘김 | 나선형 미리 읽기, 메모리 예산(기본 1GB), 장수 제한, 탐색 시 세대 번호로 낡은 작업 폐기 |
| 연속 넘김 | 키를 누르고 있는 동안 미리 읽기 중단, 미리보기만 표시 |
| 업로드 | 디코드 결과를 작업자 스레드에서 GPU 업로드 준비, UI 스레드는 그리기만 |
| 거대 이미지 | 512px 타일 + 밉맵 + LRU, 그동안 축소 대리 이미지 표시 |
| 스레드 | UI 스레드는 디코드 금지. 결과는 채널 + `EventLoopProxy`로 깨움 |

**취소 모델**: 탐색마다 세대 번호(AtomicU64) 증가. 디코더는 단계 사이에서 `CancelToken` 확인, 끝까지 진행된 낡은 결과는 캐시 정책에 따라 보관 또는 폐기. 캐시가 디코드 결과의 **유일한 소유자** (ImageGlass의 추적 누락 누수 방지).

**측정 우선**: M0에서 `iv bench`로 형식별 probe/preview/decode 시간을 측정하고, 이후 모든 최적화는 측정치로 판단.

| 목표치 (측정 전 가설) | 값 |
|---|---|
| 캐시된 이미지로 넘김 → 화면 표시 | 1프레임(16ms) 이내 |
| 24MP JPEG 미리보기 표시 (콜드) | 50ms 이내 |
| 실행 → 첫 이미지 미리보기 | 150ms 이내 |

## 5. 형식 지원 계획 (크레이트 버전은 2026-11-14 crates.io 기준)

| 형식 | 디코드 (1순위 → 보루) | 인코드 | 비고 |
|---|---|---|---|
| JPEG | `zune-jpeg` 0.5 (`image` 0.25도 내부적으로 사용) → WIC | `image` 내장 → 이후 `turbojpeg`/mozjpeg | 무손실 회전: `turbojpeg` 1.5 (C 빌드 필요, M4 이후) |
| PNG | `image` 0.25 (`png`) | `image` + `oxipng` 10 최적화 | |
| WebP | `image-webp` 0.2 → WIC | `image-webp`(무손실) / `webp` 0.3(손실, libwebp) | |
| GIF | `image` (`gif`) | `image` | 애니메이션 |
| BMP/ICO/TGA/PNM/QOI/DDS | `image` | `image` | |
| TIFF | `image` (`tiff`) → WIC | `image` | |
| AVIF | **WIC (AV1 확장)** → 이후 dav1d | `ravif` 0.13 | |
| HEIC/HEIF | **WIC (HEIF 확장)** → 이후 `libheif-rs` 3.0 | (보류) | libheif는 LGPL |
| JPEG XL | `jxl-oxide` 0.12 (순수 Rust) | `gamut-jxl` 0.5 → libjxl 0.12 (정적, `iv-libjxl`) | JPEG 무손실 재압축(jbrd), 원본 JPEG 복원은 `jxl-oxide` |
| RAW | 내장 미리보기 우선 → WIC(RAW 확장) → `rawler` 0.8 | 해당 없음 | |
| SVG | `resvg` 0.50 | 해당 없음 | |
| EXR/HDR | `image` | `image` | HDR 톤매핑은 M5 |
| PSD | (M5 이후 검토) | 해당 없음 | |

**WIC 보루 코덱**: `windows` 0.62 크레이트로 `IWICImagingFactory` 사용. OS에 설치된 코덱을 그대로 활용하므로 형식 범위가 넓고 하드웨어 가속 혜택도 있음. Windows 전용이므로 `cfg(windows)` 뒤에 격리.

**기타 크레이트 후보**

| 용도 | 크레이트 |
|---|---|
| 창/입력·대화상자 | Win32 직접 (`windows` 0.62) — M5까지는 `winit` + `wgpu` + `egui`, M6에서 교체 |
| 리사이즈 (SIMD) | `fast_image_resize` 6.1 |

### M3 결과 (2026-11-15)

- 디코더 구성 (우선순위 높은 순)

  | 형식 | 디코더 |
  |---|---|
  | JPEG | zune-jpeg → image-rs → WIC |
  | PNG/APNG, GIF, WebP, ICO, QOI, TGA, PNM, EXR, HDR | image-rs (애니메이션 포함) |
  | TIFF, BMP, DDS | image-rs → WIC |
  | AVIF | rav1d → WIC (rav1d 실패 시에만) |
  | HEIF/HEIC, Camera RAW | WIC (내장 썸네일을 미리보기로) |
  | JPEG XL | jxl-oxide → WIC |
  | SVG/SVGZ | resvg (긴 변 1024~8192로 래스터화) |

- 확인된 사실과 그에 따른 결정
  - Windows AV1 코덱은 AVIF 알파를 버림 (ffmpeg 디코드로 파일의 알파 1~254 확인 후 비교) → rav1d 경로 추가, 내용 기반 선택을 위한 `Decoder::claims` 확장 지점 추가
  - **(M4에서 정정)** 처음에는 불투명 AVIF를 회전·ICC 때문에 WIC에 맡겼으나, M4 인코더 왕복 테스트에서 Windows AV1 코덱이 BT.601 파일을 BT.709로 디코드함을 발견 (순수 빨강 → (255,25,0); ffmpeg·rav1d는 (254,0,0)). libavif의 8비트 sRGB 기본값이 BT.601이므로 실사용 AVIF 다수에 영향 → 모든 AVIF를 rav1d로. 남은 한계였던 AVIF 컨테이너 회전(irot/imir)과 내장 ICC는 2026-11-17에 해결 (아래 "AVIF 컨테이너 방향과 ICC")
  - avif-decode의 10비트 출력은 이미 16비트 범위 (실측 56503 ≈ 220×257) → 처음 넣었던 추가 확장은 테스트에서 흰색으로 드러나 제거
  - WIC는 잘린 PNG를 성공으로 반환 → PNG/GIF/ICO/WebP는 WIC 보루에서 제외(손상 파일은 오류로 보고)
  - WIC의 AVIF 미리보기는 사실상 전체 디코드(9.2MP에서 46ms/76ms)이고 알파도 없음 → AVIF 미리보기 생략
- 애니메이션: GIF/WebP/APNG 프레임 전체 합성, 0~10ms 지연은 100ms(브라우저 규칙), 512MiB 초과 애니메이션은 첫 프레임만, 캐시는 모든 프레임 메모리를 계산. 실제 창에서 20프레임×100ms가 2001ms에 한 바퀴
- 색 관리: 내장 RGB ICC → sRGB (moxcms, 8/16비트, 모든 프레임). 기준값 검증: P3 (234,51,35) → sRGB (255,0,0) ±4. sRGB 태그 이미지는 대표색 125개 왕복으로 항등을 확인해 변환 생략(9.2MP 변환 13ms 절약)
- RAW: 형식 식별(RAF/ORF/RW2/CR3 서명, TIFF 기반은 확장자)과 WIC 경로는 구현. **실제 RAW 파일로는 아직 검증하지 못함** (이 컴퓨터에 샘플 없음)
- 빌드 요구 사항에 NASM 추가 (rav1d 어셈블리)
- 자동 창 검사는 `--no-activate`로 실행 (테스트 창이 포커스를 가져가 다른 앱의 키 입력을 받는 일이 실제로 있었음)

### JPEG XL 인코딩 (2026-11-17)

- 인코더를 `zune-jpegxl`(무손실만, 메타데이터 없음)에서 참조 구현 libjxl 0.12로 교체. 안전한 Rust 계층은 `gamut-jxl` 0.5 (MIT/Apache-2.0, `encode` 기능만: 디코딩은 계속 `jxl-oxide`)
- libjxl 빌드: `gamut-jxl-sys`는 `jpegxl-src`의 `build()`로 빌드하는데, 이것이 CMake에 ClangCL 도구 집합(Visual Studio 선택 구성 요소)을 요구해 Build Tools 기본 설치에서는 MSB8020으로 실패함. 그래서 `.cargo/config.toml`의 `[env] GAMUT_JXL_SYS_SKIP_NATIVE=1`로 그 빌드를 끄고, 새 크레이트 `iv-libjxl`의 build.rs가 같은 소스(`jpegxl-src-0.12.0/libjxl`)를 기본 MSVC 도구 집합으로 빌드해 `jxl`·`jxl_cms`·`hwy`·`brotli*`를 정적 링크. `cmake` 크레이트가 MSVC 플래그를 자기 것으로 바꾸면 최적화(/O2)와 C++ 예외 해제(/EHsc)가 빠지므로 CMake 기본 플래그를 직접 주고, C 런타임은 `CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded`(/MT). 디버그 빌드에서도 항상 Release로 빌드(처음 한 번 약 1–2분). CMake가 PATH에 없고 `CMAKE`도 없으면 build.rs가 `vswhere`로 Visual Studio C++ 워크로드의 CMake를 찾아 씀 (Build Tools는 PATH에 넣지 않으므로; 없으면 빌드 스크립트가 다시 돌 때마다 `scripts/cache.ps1`까지 실패했음)
- 옵션: `quality` 1–100(libjxl `JxlEncoderDistanceFromQuality`와 같은 식으로 거리로, 100은 무손실), `lossless`, `effort` 1–9, `lossless_jpeg`. 기본은 `cjxl`과 같음: JPEG은 무손실 재압축, 그 밖은 quality 90(거리 1.0)·effort 7
- 메타데이터: RGB ICC는 코드스트림에(libjxl이 아는 색 공간이면 코드로 줄여 담음), EXIF는 컨테이너 `Exif` 상자에. 메타데이터가 없으면 컨테이너 없는 코드스트림
- 내보내기(`iv-pipeline/src/export.rs`): JPEG 원본 + 회전·뒤집기만 + `lossless_jpeg`면 `Encoder::recompress_jpeg`(libjxl `JxlEncoderAddJPEGFrame` + `StoreJPEGMetadata`). 방향은 libjxl이 넘겨받은 JPEG의 EXIF에서 읽으므로, JPEG 회전과 같은 방식으로 EXIF 방향을 고친(또는 `--no-metadata`면 메타데이터를 뺀) JPEG을 넘김. 아무것도 바꾸지 않으면 원본 바이트를 그대로 넘겨 원본 복원이 바이트 단위로 같게 함. libjxl이 거부하면(CMYK, 산술 부호화 등) 픽셀 인코딩
- 방향 확인(`recompress_as`): libjxl(`lib/jxl/base/exif.h`의 `InterpretExif`)은 첫 EXIF APP1의 SHORT·개수 1인 방향 태그만 읽고, 뷰어(zune-jpeg + kamadak-exif)는 마지막 EXIF 세그먼트를 쓰고 LONG도 읽음. 그래서 재압축 결과의 JPEG XL 헤더 방향(`iv_codec::jxl_orientation`)을 뷰어가 보여 주는 방향과 비교하고, 다르면 `exif_edit::jpeg_with_orientation`으로 모든 EXIF 세그먼트의 방향 태그를 SHORT·개수 1로 고쳐 한 번 더 재압축, 그래도 다르면 픽셀 인코딩. `jpeg_with_orientation`은 JPEG 무손실 회전에서도 모든 EXIF 세그먼트를 고침(전에는 첫 세그먼트만 고쳐 뷰어가 읽는 마지막 세그먼트는 그대로였음)
- JPEG XL → JPEG XL(회전·뒤집기만, `lossless_jpeg`): 복원 정보가 있으면 원본 JPEG을 되살려 EXIF 방향을 고친 뒤 다시 재압축(`JpegRecompressed`). 뷰어의 제자리 저장(`lossless=true`)도 이 길: 전에는 무손실 픽셀 인코딩으로 2.7배 커지고 복원 정보가 사라졌음
- 디코더(`builtin/jxl.rs`): 컨테이너의 상자 머리만 읽고 건너뛰며 `Exif` 상자를 찾음. libjxl은 픽셀 인코딩 때 이 상자를 코드스트림 뒤에 쓰는데, jxl-oxide는 다음 상자가 와야 상자를 내주므로 마지막 상자는 볼 수 없음. 재압축 때 libjxl이 쓰는 Brotli 압축 상자(`brob`)만 jxl-oxide로 풂
- 흑백: 흑백 ICC가 있고 모든 픽셀이 회색이면 `Gray8/16`(알파가 있으면 `GrayAlpha`)으로 그 프로필과 함께 씀. 편집으로 색이 생겼으면 프로필 없이 sRGB
- 원본 JPEG 복원: JPEG XL → JPEG(회전·뒤집기만)이면 `jxl-oxide`의 `reconstruct_jpeg`(`jxl-jbr` 0.2.1)로 복원한 뒤 JPEG 회전과 같은 EXIF 경로. `jxl-jbr` 0.2.1은 주석(COM) 세그먼트의 표지 바이트를 두 번 씀(`FF FE FE …`: libjxl이 저장한 주석에 이미 표지 바이트가 있음) → `iv-codec`의 `undouble_comment_markers`가 바로잡음 (뒤따르는 길이로 다음 표지에 정확히 닿을 때만). 복원물이 읽히지 않으면 픽셀 인코딩
- 뷰어: JPEG XL을 그 자리에 저장하면(같은 파일로 다른 이름으로 저장 포함) `lossless=true`를 더해 항상 무손실. 다른 이름으로 저장은 저장 품질 슬라이더가 `quality`. 채널당 16비트를 넘는(부동소수점) 이미지는 `InPlace::keeping_depth`가 `TooDeep`으로 바꿔 다른 이름으로 저장으로 보냄: `prepare`가 부동소수점을 8비트로 줄이고 `gamut-jxl`에는 float 입력이 없어 그대로 쓰면 HDR 값이 잘림 (`testdata/jxl/float-hdr.jxl`: libjxl API로 만든 4×2 float 무손실 파일, 165 B)
- 고지: `scripts/notices.ps1`이 빌드 의존성(`jpegxl-src`)에서 빌드되어 들어가는 libjxl·highway·brotli·skcms의 LICENSE·PATENTS도 넣음
- 시험: 손실 품질별 크기·PSNR, 거리 대응, effort, 알파·16비트 손실/무손실, ICC(코드로 줄인 것과 그대로 둔 것)·EXIF 상자, JPEG→JXL 무손실 재압축(작아짐, 디코드 결과 PSNR, ICC 유지, `--no-metadata`), 회전, JXL→JPEG 바이트 동일 복원, 픽셀 인코딩으로 넘어가는 경우(자르기, `lossless_jpeg=false`, PNG, CMYK, 방향 태그 없는 EXIF), 뷰어 제자리 저장의 무손실. 검토 후 추가: EXIF 방향 SHORT 6·LONG 6·세그먼트 둘(어느 쪽이 다르든)인 JPEG의 재압축 방향, 재압축한 JPEG XL의 회전(기본값과 `lossless=true`, 크기 유지·복원 정보 유지·되돌리면 바이트 동일·`--no-metadata`·픽셀 인코딩에서 EXIF 유지), `Exif` 상자 읽기, 흑백 ICC, float JPEG XL 디코드와 제자리 저장 거부, `set_orientation`의 LONG→SHORT, 모든 EXIF 세그먼트 수정
- 측정 (i5-14600K, 릴리스): Windows 배경 화면 JPEG 3장(3840×2400) 무손실 재압축 826 734 → 659 500 B(−21%), 1 602 752 → 1 134 487 B(−30%), 1 150 704 → 799 836 B(−31%), 한 장 약 0.3초, 되살린 JPEG은 3장 모두 원본과 바이트 동일. 같은 사진(PNG 2.37 MB)의 손실 JPEG XL: quality 90 148 613 B(3.4초), 75 83 286 B, 50 55 110 B, 무손실 1 446 914 B. 실행 파일: image-viewer.exe 18 808 832 → 22 592 000 B, iv.exe 17 178 624 → 20 958 720 B (+3.6 MiB씩), libjxl 빌드 77초(-j 3)
- 검토 후 수정 측정: Windows 잠금 화면 JPEG(3840×2160) 1 033 330 → 740 816 B(−28%, 285 ms), 되살린 JPEG 바이트 동일. 같은 JPEG에 LONG 형식 방향 6 태그를 넣으면 2160×3840 JPEG XL(전에는 돌지 않은 3840×2160), 두 번 재압축이라 543 ms. - 남은 것: `gamut-jxl`은 libjxl의 병렬 실행기를 쓰지 않아 한 장을 한 스레드로 인코딩함 (일괄 변환은 파일 단위로 병렬). ### AVIF 컨테이너 방향과 ICC (2026-11-17)

- 읽기(`iv-codec/src/builtin/heif.rs`): avif-parse 2.1은 `irot`·`imir`·`colr`을 내놓지 않으므로 `meta` 상자(`pitm`, `iprp`의 `ipco`·`ipma`)를 직접 읽음. 32/64비트·끝까지(크기 0) 상자, `ipma` 버전 0/1과 7/15비트 속성 번호, `pitm` 버전 0/1. 모든 읽기는 경계 검사, 읽지 못한 속성은 건너뜀(깨진 EXIF 방향 태그와 같은 취급: 파일 구조는 avif-parse가 이미 받아들임)
- 방향: `irot`는 반시계 90°×n → 1 = `Rotate270`, 2 = `Rotate180`, 3 = `Rotate90`. `imir`의 axis 0은 위아래를 바꿈(`FlipV`, EXIF 4), 1은 좌우를 바꿈(`FlipH`, EXIF 2) — ISO/IEC 23008-12:2022 6.5.12. 변환 속성은 `ipma`에 적힌 순서대로 합성(HEIF 규칙, MIAF가 그 순서를 clap → irot → imir로 고정). 회전 뒤 뒤집기 조합은 libavif의 EXIF 대응표와 같음(irot 1 + axis 0 = EXIF 5, + axis 1 = EXIF 7 …)
- 보고 방식은 JPEG EXIF와 같음: `width`·`height`는 저장된(부호화된) 크기, `orientation`이 보여 줄 때의 변환, 표시 크기는 `display_size()`. probe와 decode가 같은 함수(`header`)로 읽으므로 크기·방향·프로필이 항상 같음. 화면(`raster`의 UV 변환)과 저장(`Geometry` → `apply::render`)은 손대지 않고 그대로 따름
- ICC: 첫 `colr`의 `prof`/`rICC` 프로필을 `icc_profile`로 넘겨 다른 형식과 같은 색 관리(moxcms → sRGB). `nclx`는 프로필이 아님: YUV 행렬·범위는 avif-decode가 AV1 시퀀스 헤더에서 가져오고(지정 없으면 BT.601) 컨테이너의 `nclx`는 보지 않음, 원색·전달 함수(P3·BT.2020·PQ 등)는 색 관리하지 않아 sRGB로 간주. 깨끗한 조리개(`clap`) 자르기도 적용하지 않음(부호화된 전체를 보여 줌)
- WIC 대체 디코더(rav1d가 실패할 때만): Windows AV1 코덱은 `irot`/`imir`를 스스로 적용해 똑바른 크기와 `Normal`을 보고 → 12가지 조합 모두 rav1d 경로와 네 모서리 배치가 같음(테스트). ICC는 보고하지 않지만 프로필을 무시하는 것도 아님: 코덱이 스스로 프로필에 반응하는데 색 변환이라 볼 수 없는 결과를 냄. 48×32 사분면 AVIF에서 프로필 없음·`nclx`·sRGB 프로필은 같은 결과(빨강 (213,73,37), 흰색 (228,228,228)), Display P3 프로필(moxcms, `cicp` 태그 유무 무관)이면 빨강 (200,94,100)·흰색 (128,128,228)(같은 D65 흰색이 파랗게), BT.2020 프로필이면 모든 색이 밝아짐(흰색 (243,243,243))과 함께 채널당 16비트로 보고. 그래서 컨테이너의 프로필을 대신 넘기면 코덱 결과 위에 한 번 더 적용될 뿐이라 넘기지 않음(검토 후 시도해 보고 되돌림; 프로필을 보고하지 않음은 `the_wic_fallback_reports_no_profile_of_its_own`이 고정). sRGB가 아닌 프로필이 든 AVIF가 rav1d에서 실패하면 색이 틀린 채 보임 → 대체 경로의 한계로 남김
- 독립 확인: 같은 12개 파일을 ffmpeg 9.0.2로 디코드(자동 회전)해도 네 모서리 배치가 모두 같음
- 저장: 내보내기는 방향을 픽셀에 굽고 AVIF 인코더는 `irot`/`imir`를 쓰지 않으므로 결과는 `Normal`. 이번에 드러난 문제: AVIF 인코더(ravif/avif-serialize)는 ICC를 담지 못해, 프로필은 버려지고 픽셀은 원래 색 공간 그대로 저장돼 색이 바뀌었음(P3 JPEG → AVIF도 같음). `EncoderInfo::embeds_icc`(JPEG·PNG·WebP·JPEG XL·TIFF 참, AVIF·BMP·QOI·GIF 거짓 — 테스트가 인코더마다 실제 왕복으로 확인)가 거짓이고 메타데이터를 유지하면 `color::image_to_srgb`로 sRGB로 바꿔 저장. `--no-metadata`는 종전대로 프로필만 뺌
- 곁가지 발견: image 0.25.10의 TIFF 디코더는 디코드 제한을 걸면 태그 값 개수를 픽셀 버퍼 크기로 묶어, 32×16 TIFF는 600바이트 ICC를 읽지 못함(128×96이면 읽음). 실제 사진 크기에서는 문제없어 그대로 둠
- 시험: 상자 읽기 단위 시험(각 회전·뒤집기, libavif 대응표 8가지, `ipma` 순서, 다른 항목의 속성·번호 0·범위 밖 번호 무시, 64비트·크기 0 상자와 32비트 번호, `prof`/`rICC`/`nclx`, 모든 앞부분 잘림과 바이트 하나씩 바꾼 파일에서 패닉 없음). 인코더가 쓴 48×32 AVIF에 `irot`/`imir`/`colr`를 덧붙인 파일(`iv-codec/tests/support/avif_props.rs`, `iloc` 오프셋 이동 포함)로: 회전 4 × 뒤집기 3 = 12가지에서 저장 픽셀 그대로·probe = decode·표시 크기·화면 변환 결과 = HEIF 정의를 픽셀 인덱스로 직접 계산한 결과(8가지 방향 모두 나옴), 모서리 배치, P3 프로필 전달·색 관리 = moxcms 기준 ±1, WIC 대조. 내보내기: 회전·뒤집힌 AVIF → PNG(픽셀 일치, 32×48) → 시계 방향 회전 후 AVIF 제자리 저장(PSNR > 35 dB), P3 AVIF → PNG(프로필·픽셀 유지) / → AVIF(sRGB로 변환, 보이던 색 ±4) / `--no-metadata`(픽셀 그대로). 새 시험은 고치기 전 코드에서 모두 실패(디코더 4개, 내보내기 2개; 내보내기만 되돌리면 ICC 시험 1개)
- 실제 실행: `iv probe` → `Transverse`/`Rotate90`, `iv convert --to png` → 32×48, ffmpeg의 AVIF 디코드와 네 모서리 색 일치. 실제 창(`--no-activate`, 자기 창 `PrintWindow`, 200% 모니터): 480×320 AVIF + irot 1 + imir 1 → 제목 "320×480", 100%에서 위 왼쪽부터 흰색·초록·파랑·빨강(= 저장된 오른쪽 아래·오른쪽 위·왼쪽 아래·왼쪽 위), P3 프로필 AVIF는 왼쪽 위 사분면이 (201,61,40) → (219,43,23)으로 색 관리됨, 창이 포커스를 가져가지 않음

### M6: Win32 직접 프런트엔드 (2026-11-15 결정)

목표: 극도로 작고 빠른 뷰어. wgpu + egui 창(`iv-app`, `iv-render`)을 순수 Win32 창(`iv-win`)으로 교체.

결정 근거 — 같은 PC(RX 9060), 같은 3840×2400 JPEG, `iv-win/examples/backend_probe.rs`로 측정:

| 표시 방식 | Private bytes | 첫 화면 (디코딩 ~50 ms 포함) |
|---|---|---|
| 빈 Win32 창 | 1.4 MB | 6 ms |
| GDI + CPU 확대·축소 (fast_image_resize SIMD) | 40 MB (이미지 자체가 37 MB) | 89~127 ms |
| Direct2D (D3D11 드라이버 로드) | 137~141 MB | 146~199 ms |
| 기존 wgpu DX12 + egui | 382 MB | — |

GPU를 쓰는 순간 드라이버(AMD `amdxc64.dll` 등)가 100 MB대 바닥을 깔기 때문에 GDI + CPU 경로를 택함.

구조:

- `raster`: 플랫폼 독립 CPU 렌더러 (테스트 가능). 화면에 보이는 부분(+ 필터가 닿는 몇 픽셀)만 원본에서 잘라 화면 크기로 리샘플(소수점 crop, 알파 premultiply도 그 부분만) → 방향(D4) 적용 → 보정(`ToneTable`, 저장과 같은 표) → 투명 체커·선택 영역 어둡게 → BGRA 프레임. 절반 이하로 줄여 보일 때는 박스 필터로 만든 1/2·1/4 … 크기 단계(밉 레벨)에서 리샘플(쓰는 단계 하나만 보관). 이미지 전체를 BGRA로 복사하거나 회전본을 만들지 않으므로 추가 메모리는 화면 크기 정도(+ 밉 레벨)
- `view`: 확대·이동 수학 (`iv-render`에서 이전)
- Win32 셸: 창·메시지 루프·키보드(VK → keymap 이름)·마우스·끌어 놓기·전체 화면·우클릭 메뉴, 파이프라인 이벤트는 채널 + `PostMessageW`
- 편집 패널·설정: 기본 Win32 컨트롤(트랙바·버튼·입력란, comctl32 v6), 색 선택은 `ChooseColorW`, 파일 대화상자는 `IFileDialog` 직접 호출 (`rfd` 제거)
- commands / keymap / settings / edit는 `iv-app`에서 그대로 이전

완료 기준: 기존 기능 전부(넘김·빠른 넘김·미리보기 먼저·애니메이션·두 쪽 보기·압축파일·편집·저장·설정·단축키) 동작, `iv-app`·`iv-render` 제거, 메모리·첫 화면 시간 측정 기록.

### 출시 전 점검: 창·입력·상태 (2026-11-17)

- 창 크기 반영: `WM_SIZE`는 창 프로시저가 받아 "대기 중인 크기"로 두고, 앱이 다음에 큐를 비울 때 적용. 전체 화면 전환의 `SetWindowPos`처럼 앱이 바쁜 동안 동기로 오는 `WM_SIZE`가 버려져 전체 화면에서 이미지가 왼쪽 위 1280×800에만 그려지던 문제 수정 (모달 대화상자 중의 크기·DPI 변경도 같은 경로)
- 그리기: `WM_PAINT`는 앱 큐를 비우지 않고 렌더만 한 뒤 화면에 옮기고, 프레임을 놓은 다음에 큐를 비움. 그리기 도중 큐에서 저장 실패 대화상자가 열리면 중첩 그리기가 `FRAME`을 두 번 빌려 프로세스가 중단되던 문제 수정. 중첩 그리기는 프레임이 바쁘면 창만 유효화
- 한글 IME: 뷰어 창에는 입력기를 연결하지 않음(`ImmAssociateContextEx`). 남는 경우를 위해 `VK_PROCESSKEY`는 스캔 코드로 실제 키를 복원 → 한글 모드에서도 R·F·D 등 한 글자 단축키 동작. 패널·설정 창 입력란은 입력기 유지
- 폴더 열기: 명령줄·끌어 놓기로 폴더를 주면 그 폴더 이미지를 자연 정렬 첫 장부터. 폴더가 이미지 목록 항목으로 끼어들지 않음
- 마우스: 앞으로/뒤로 버튼(`Mouse5`/`Mouse4`) = 다음/이전, 휠·버튼은 키맵 이름(`WheelUp`, `WheelDown`, `Mouse4`, `Mouse5`, 수정 키 포함)으로 다시 묶을 수 있음. 설정 "휠로 사진 넘기기"를 켜면 휠 = 이전/다음, Ctrl+휠 = 확대. 휠 명령은 한 칸(120)마다 한 번, 메시지당 최대 한 번(정밀 휠·터치패드 대응)
- 빠른 넘김 중 포커스를 잃으면(`WM_KILLFOCUS`) 빠른 넘김을 끝내고 미리 읽기 재개
- 빠른 넘김 중 지나가며 띄운 애니메이션이 현재 이미지가 되면 재생 시작
- 제목 표시줄: 같은 문구면 다시 쓰지 않음(이동 중 매 마우스 이동마다 쓰던 것 제거). 일회성 알림(두 쪽 보기에서 편집 거부, 저장 실패, 설정 저장 실패 등)은 파일 이름·크기·편집 표시 뒤에 붙고 6초 뒤 또는 다음 명령에서 사라짐. 파일을 열 수 없는 오류만 다음 파일까지 남음
- 오류 문구 번역: 디코드 실패는 종류별(지원하지 않는 형식, 파일 없음, 너무 큼)로 한국어·영어 문장, 그 밖은 "열 수 없습니다 (원문)". 저장 요청 오류(알 수 없는 확장자, 쓸 수 없는 형식)도 번역
- 선택 영역: 이미지 픽셀 좌표로 보관 → 확대·이동·창 크기 변경 후에도 같은 부분이 선택되어 있고, 어둡게 하지 않은 영역 = 자르기 결과(픽셀 경계에 맞춤)
- 창 크기: 처음 열 때 주 모니터 DPI에 맞춘 1280×800 논리 픽셀(작업 영역보다 크면 줄임), 가운데. 닫을 때 복원 위치·크기·최대화 여부를 설정 파일 옆의 상태 파일 `window.toml`에 기록(`settings.toml`은 설정 창의 저장만 쓰므로 창을 닫는 것만으로 생기거나 다시 쓰이지 않음: 기본값이 파일에 굳지 않고 손으로 고친 값·주석·서식이 보존됨. 같은 위치면 다시 쓰지 않고, 망가진 상태 파일은 무시했다가 다음 닫을 때 교체)하고 다음 실행 때 그 모니터에서 복원. 연결이 끊긴 모니터나 제목 표시줄이 화면 밖인 위치는 무시
- 편집 패널·설정·도움말 창: `WM_DPICHANGED` 처리(제안된 사각형으로 이동, 모든 컨트롤을 96 DPI 기준 좌표에서 다시 배치, 새 DPI 글꼴)
- 설정 창: 입력란을 떠날 때 범위 밖 값은 실제로 적용된 값(clamp)으로 다시 표시, 저장 직전에도 화면 = 저장값
- 편집 패널: 크기 입력란을 비우거나 잘못된 값이면 그 값을 0으로 보고해 적용 버튼이 꺼짐(예전에는 마지막 유효 값으로 적용됨). 비율 유지 중 비운 칸은 다른 칸을 바꾸지 않음
- 두 쪽 보기와 편집: 쪽 배치가 편집된 크기를 따름(회전한 쪽이 늘어나 보이던 문제, 두 쪽 보기를 끄면 편집 전 크기로 돌아가던 문제 수정). 두 쪽 보기 중 실행 취소·다시 실행도 배치를 다시 계산
- 제자리 저장 직후: 새 디코드가 올 때까지 옛 픽셀을 저장한 편집 그대로 그림(회전·자르기 크기에 원본이 늘어나 보이던 문제 수정)

### 출시 전 점검: 견고성 (2026-11-17)

- 패닉 격리: `iv_core::panic::catch`가 패닉을 `Error::Panicked`("{무엇} crashed: …")로 바꿈. `Registry`는 디코더의 `claims`·`probe`·`preview`·`decode`와 색 관리를 하나씩 감싸 패닉한 디코더를 실패한 디코더로 취급(다음 우선순위로 넘어감). 디코드 작업자는 압축파일 읽기까지 포함한 작업 전체를, 저장 스레드는 내보내기를, `iv convert`는 파일마다, 폴더·압축파일 목록 읽기도 감쌈. 예전에는 디코더 하나가 패닉하면 작업자 스레드가 `in_flight`·전경 표시를 남긴 채 죽어 그 뒤로 어떤 이미지도 열리지 않았고(전경 작업자 1개), 저장 스레드가 죽으면 "저장하는 중"이 풀리지 않았음. 할당 실패·스택 넘침은 여전히 프로세스를 끝냄
- 진단: 릴리스는 콘솔이 없으므로 `diag::log`가 stderr와 함께 `%LOCALAPPDATA%\image-viewer\image-viewer.log`에 씀(첫 메시지 때 생성, 256 KiB 이상이면 다음 실행에서 비움, 실행당 128 KiB, 여러 창이 함께 써도 덧붙이기). 패닉 훅: 창 스레드의 패닉(창 프로시저 경계에서 프로세스가 중단됨)은 `crash.log`(마지막 한 건)에 메시지·위치·백트레이스를 쓰고, 별도 스레드의 소유자 없는 메시지 상자로 경로를 알림(창 스레드의 메시지 루프를 돌리지 않음). 쓰지 못하면 상자는 다른 문구(`crash_unsaved`: 이유 + 메시지·위치)로, 로그에도 실패를 남김. 백트레이스는 전체 형식(`{:#}`: 기호가 없는 프레임도 주소를 남김. 짧은 형식은 `<unknown>`만 씀)이고, 이 실행 파일 안의 프레임마다 `[이름+오프셋]`을 붙임. 보고서의 `image:` 줄은 실행 파일의 시작 주소·`SizeOfImage`·링크 시각·.pdb 이름/GUID/age로, 메모리에 올라온 자기 PE 헤더를 `__ImageBase`(링커 기호)에서 직접 읽음(std만, Windows API 없음). 배포 zip에는 .pdb가 없어(symbols zip에 따로) 뷰어 프레임은 이름이 없으므로, `scripts/symbolize.ps1`이 같은 릴리스의 exe와 .pdb로 dbghelp(`SymLoadModuleEx`에 임의 기준 주소 + 오프셋, 반환 주소라 1을 빼서 조회, `SYMOPT_EXACT_SYMBOLS`)를 불러 이름·파일:줄을 붙임. 링크 시각이 다르면 다른 빌드라고 경고. 격리된 패닉과 다른 스레드의 패닉은 로그에만. 창 생성 실패도 메시지 상자로, 폴더 목록 실패는 제목 표시줄 알림으로(예전에는 stderr에만 써서 이전·다음이 말없이 안 됨)
- SVG: `usvg`의 기본 `image_href_resolver`는 `data:`가 아닌 href를 파일 경로로 읽음 → 바깥 파일을 그림에 끼워 넣거나 `\\호스트\공유` 경로로 SMB 연결(NTLM 자격 증명 전송)을 일으킬 수 있었고, 미리 읽기 때문에 폴더를 넘겨 보기만 해도 일어남. 문자열 href는 모두 거부하고 `data:`만 그림
- 압축파일: 헤더의 크기는 첫 할당(최대 64 MiB)에만 쓰고, 선언 크기가 1 GiB(`MAX_ENTRY_BYTES`)를 넘거나 실제로 풀린 양이 넘으면 오류(압축 폭탄, `u64::MAX` 크기로 인한 capacity overflow 패닉 방지). ZIP 압축 크기가 압축파일보다 크면 거부. 항목 이름은 `\` → `/`로 정규화하고(PowerShell 5 `Compress-Archive` 등이 쓴 CBZ의 하위 폴더 페이지가 목록에는 있는데 열리지 않던 문제), 절대 경로·드라이브·`:`·`.`/`..`·빈 구성 요소가 있는 이름은 버림(가상 경로가 압축파일 밖 실제 파일을 가리키던 문제). 7z 캐시: 128 MiB, 압축파일 하나(경로·크기·수정 시각)의 항목만, `Arc<[u8]>`로 나눠 써 적중 때 복사 없음, 압축파일 밖 이미지를 열면 비움. 7z 헤더도 한도 안: 풀린 헤더는 17 MiB(`SEVEN_Z_HEADER_KIB`)를 넘으면 읽다가 멈추고 오류. 크레이트는 같은 한도를 헤더를 푸는 디코더의 메모리(사전 + 상태)에도 적용하므로 16 MiB + 1 MiB: py7zr이 기본으로 쓰는 LZMA2 16 MiB 사전(16 488 KiB 필요, 7-Zip은 1 MiB, `sevenz-rust2` 작성기는 8 MiB)까지 열림. 16 MiB 한도일 때는 py7zr로 만든 7z가 모두 열리지 않았음, 64 MiB로 올리면 적대적 헤더의 해석 비용이 네 배라 택하지 않음(예전에는 몇 KB의 LZMA 헤더가 선언한 만큼 GB 단위로 풂). 크레이트가 모든 개수를 헤더 길이로 묶으므로 해석한 목록은 헤더 1바이트당 항목 하나(96바이트)가 최악 → 적대적 헤더도 잠시 약 1.7 GB가 상한, 실제 헤더는 파일당 50~100바이트라 15만 개 이상 나열. 블록의 압축 사전은 1 GiB + 1 MiB(`SEVEN_Z_DICTIONARY_KIB`)를 넘으면 풀기 전에 거부. 블록은 한 스레드로 풂: 다중 스레드 LZMA2 리더는 사전 초기화 사이 구간을 통째로(구간 하나가 블록 전체일 수도) 여러 스레드에서 미리 메모리에 풀어 항목 한도가 소용없음. 한도 밖에 남는 것: 크레이트의 헤더 해석 중 임시 할당(위 상한), 7z 캐시 128 MiB
- 메모리 상한: 미리 읽기도 헤더를 먼저 읽어 예상 크기(RGBA, 정밀도·알려진 프레임 수 반영)가 예산의 절반을 넘으면 디코드하지 않고 사용자가 열 때까지 둠. 실행 중 디코드의 예상 크기 합(`reserved_bytes`)이 예산을 넘으면 다음 미리 읽기는 기다림(현재 이미지는 기다리지 않음). 사용자가 미리 읽는 중인 이미지로 넘어오면 새 작업을 만들지 않고 그 미리 읽기가 현재 이미지의 불러오기가 됨: 예산 대기를 멈추고, 아직 보내지 않았으면 `Probed`·`Preview`를 보내고, "미리 읽기엔 너무 큼" 판정을 건너뛰며 결과를 캐시에 둠. 판정 직후 넘어온 경우는 그 자리에서 전경 작업을 다시 넣음(그 미리 읽기가 이미 취소됐다면 넣지 않음: 사용자가 떠났다 돌아오며 이미 새 불러오기를 시작했으므로 같은 큰 이미지를 두 번 디코드하지 않음) (예전에는 화면이 빈 채 남거나 다른 디코드가 끝날 때까지 미리보기 없이 기다림). image-rs 경로는 출력 크기 버퍼 하나를 `try_reserve_exact`로 잡고(실패하면 "너무 큼" 오류. 레지스트리는 어느 디코더든 "너무 큼"이라 하면 그 오류를 그대로 넘겨 화면에 "너무 커서 열 수 없음"과 크기가 나옴, 예전에는 `NoDecoder` 문장에 묻힘) 디코더가 그 안에 쓴 뒤 제자리에서 RGBA로 넓힘 → 16비트·부동소수 이미지의 두 번째 전체 복사 제거, RGB 8비트도 중간 버퍼 없음
- 취소와 넘김: 미리 읽기 작업자도 현재 이미지 작업을 먼저 가져감 → 버려진 긴 디코드(디코더는 단계 사이에서만 취소 확인)가 끝날 때까지 Home/End·새 파일 열기가 기다리지 않음. 전경 실행 목록은 여러 개(토큰과 함께), `in_flight`는 경로마다 가장 새 작업의 토큰만 지움. 취소된 디코드가 아직 도는 이미지로 바로 돌아오면 새 작업을 시작(예전에는 취소된 작업이 아무것도 알리지 않아 그 이미지가 영영 안 열림)
- 빠른 넘김과 작업자 가로채기: 빠른 넘김 중에는 실행 중인 전경 디코드를 하나도 취소하지 않고, 살아 있는(취소되지 않은) 전경 디코드가 끝나야 다음 전경 작업(그 시점의 최신 요청)이 어느 작업자에서든 시작(`foreground_may_start`). 취소된 채 아직 도는 디코드는 기다리지 않음. 예전(가로채기 도입 직후)에는 키 반복마다 빈 미리 읽기 작업자가 새 전경 디코드를 시작하고 "가장 새 것만 유지" 규칙이 그보다 먼저 시작한 디코드를 취소 → 큰 사진 위에서 키를 누르고 있으면 지나가는 사진이 거의 표시되지 않고 놓을 때까지 화면이 멈춤. 한 번에 하나만 돌리므로 지나가는 사진이 순서대로 표시되고 CPU를 나눠 쓰지 않음
- 테스트: 패닉 디코더(폴백·`NoDecoder` 이유), 패닉이 작업자 수보다 많이 나도 이후 이미지가 열림, 정지된 디코드 중 새 이미지가 바로 열림, 취소된 이미지로 돌아가기, 빠른 넘김(작업자 4개, 정지된 디코드 중 요청 3번 → 한 번에 하나만 디코드, 먼저 시작한 사진도 알림·캐시, 건너뛴 요청은 디코드 안 함 / 버려진 디코드를 기다리지 않음), 미리 읽기 예약이 예산 안(2장까지, 3번째는 대기), 예산 절반 넘는 이웃은 미리 읽지 않음, SVG 바깥 파일(절대·`file://`·상대 경로) 미사용과 `data:` 이미지 표시, `\` 이름·탈출 이름·4 GiB 선언 크기·1 MiB 한도 압축 폭탄, 색 형식 10종의 제자리 넓히기, 로그 덧붙이기·실행당 상한·비우기, 크래시 훅(별도 테스트 바이너리: 창 스레드 패닉 → `crash.log`(`image:` 줄과 프레임 오프셋 포함)와 메시지 1회, 격리·다른 스레드 패닉 → 로그만), 합성 PE 이미지의 .pdb 식별자 읽기와 잘린·엉뚱한 헤더(패닉 없이 없음), 테스트 실행 파일 자신의 식별자가 디스크의 파일 속 `RSDS` 기록과 같음, 프레임 줄의 오프셋 표기, 기록을 못 쓴 경우의 상자 문구. 패닉 격리·전경 가로채기·재요청·빠른 넘김 테스트는 수정을 되돌리면 실패(시간 초과·정지)함을 확인
- 실제 창 확인 (release, `--no-activate`, 자기 창에만 메시지, `PrintWindow`, `LOCALAPPDATA`와 설정은 임시 폴더): 왼쪽 절반은 바깥 PNG(라임), 오른쪽 절반은 `data:` PNG(파랑)인 SVG → 왼쪽은 투명 체커(라임 0), 오른쪽 파랑 / `\` 구분 CBZ(`ch1\01.png`, `ch1\02.png`, `ch2\01.png`, `..\outside.png`) → 3장 목록, → 두 번에 [3/3] `ch2\01.png`(청록) / 디코드 2.46초인 7000×7000 WebP를 연 뒤 0.5초에 End → 마지막 사진이 요청 10.2 ms 뒤 표시 / 캐시 300 MiB 설정에서 7000×7000 PNG(187 MiB) 4장이 이웃인 폴더 → 미리 읽지 않음, 최대 작업 집합 28.9 MB, → 키로 열면 238 ms / 깨진 PNG → `image-viewer.log`에 실패 한 줄(294바이트), 정상 실행에서는 로그 파일이 생기지 않음 / 캐시 300 MiB, 6000×4000 노이즈 PNG(디코드 약 135~180 ms) 10장 폴더에서 Space 45번 반복(33 ms 간격) → 고친 판은 누르는 동안 50~240 ms마다 다른 사진 표시(지나가는 사진 8장 + 캐시 적중 8장, 놓으면 [7/10]에 정착), 고치기 전 판은 약 2초 동안 지나가는 사진 1장뿐(p02~p07은 한 번도 안 보임)
- 미확인: 실제 창 스레드 패닉의 메시지 상자(모달이라 자동 시험하지 않음, 훅은 테스트 바이너리로 확인), 실제 서드파티 디코더 패닉을 일으키는 표본 파일, 할당 실패(커밋 한도) 상황. JPEG·AVIF·JXL·WIC 디코더는 내부에서 할당하므로 할당 실패 시 여전히 중단될 수 있음

### 출시 전 점검: 렌더링·성능 (2026-11-17)

- 투명 이미지 다시 그리기: `fast_image_resize`는 crop을 줘도 알파 premultiply를 원본 전체에 하고, `Resizer`를 매번 새로 만들어 그때마다 원본 크기 버퍼를 잡았음(8000×6000 RGBA: 다시 그릴 때마다 192 MB 할당 + 전체 곱셈). 필터가 닿는 범위까지만 잘라(`CroppedImage`, `source_window`) 넘기도록 바꿈 → 보이는 부분만. 결과는 원본 전체로 리샘플한 것과 바이트 단위로 같음(테스트: 소수점 위치 확대·축소·가장자리·1:1·nearest)
- 불투명 RGBA: 디코드 작업자가 픽셀을 한 번 훑어 모두 불투명이면 `has_alpha`를 끔(애니메이션은 모든 프레임) → premultiply·체커 합성 생략. 스크린샷 PNG 대부분이 여기에 해당
- 100% 선명도: `ViewState`가 이미지 왼쪽 위 모서리를 화면 정수 픽셀에 맞춤(맞춤·확대·이동·창 크기 변경 모두, 반 픽셀 이하 이동). 화면을 덮는 축은 가장자리에 배경 틈이 생기지 않는 쪽으로 반올림. 렌더러는 반올림 오차 범위(1e-6)의 crop을 정수로 맞춰 1:1이면 복사 경로. 두 쪽 보기의 경계도 정수 픽셀. 예전에는 창과 이미지 폭의 홀짝이 다르거나 맞춤에서 100%로 바꾸면 이웃 픽셀이 섞여 흐려짐
- 크게 줄여 보기: 절반 이하로 보일 때는 박스 필터로 만든 1/2·1/4 … 단계에서 리샘플(그 단계도 여전히 줄이기만 하도록 선택). 처음 필요할 때 만들고 지금 쓰는 단계 하나만 보관(최대 원본 메모리의 1/4, 1/4 이하로 보이면 1/16, 절반 넘게 보이면 없음). SuperSampling(nearest 선축소)은 줄무늬·글자에 모아레가 생겨 쓰지 않음
- 다시 리샘플하지 않기: 선택 영역 끌기·편집 패널·설정 창이 열려 있는 동안(`Frame::keep_resampled`) 리샘플 결과를 보관해, 선택·보정·배경만 바뀐 다시 그리기는 픽셀별 합성만 함. 그 밖에는 그린 뒤 결과와 리샘플러 임시 버퍼를 놓음(대기 중 메모리 = 프레임만)
- 보정: `iv_ops::ToneTable` — 첫 보정의 채널별 톤 곡선(밝기·대비·감마)을 256(8비트)·65536(16비트) 단계 표로, 채도가 0인 보정만 있으면 체인 전체를 채널별 표 하나로. 감마 1이면 `powf`를 건너뜀. 화면 미리보기와 저장이 같은 표를 써 결과가 같고, 표는 픽셀별 계산과 모든 입력값에서 비트 단위로 같음(테스트)
- 16비트·부동소수 이미지: 캐시에 화면용 8비트로 넣음(디코드 작업자에서 병렬 변환, 예산도 8비트 크기로 계산, `bits_per_channel`은 원본 값 유지). UI 스레드의 변환이 사라짐. 저장은 원래대로 파일을 다시 읽어 원래 정밀도로
- 미리 읽기: 현재 이미지와 함께 예산에 들어가는 이웃(가까운 순)만 시작. 크기는 디코드한 이미지의 실제 값(계획·캐시에 있는 것만 기억), 모르면 마지막 디코드 크기로 추정. 결과를 넣으려면 더 가까운 이미지를 밀어내야 하는 미리 읽기 결과는 버리고 크기만 기억. 예전에는 큰 사진 폴더에서 넘길 때마다 가장 먼 이웃을 디코드했다가 바로 버리고 다음 넘김에 또 디코드. "예산 절반 초과는 미리 읽지 않음" 판정도 캐시에 들어갈 8비트 크기 기준
- 7z/CB7: 페이지가 든 압축 블록만 풂(`BlockDecoder`). 한 스레드, 사전 한도 1 GiB(위 "압축파일" 참고). 비솔리드는 그 페이지 하나, 솔리드는 블록 안에서 앞 페이지(어차피 풀어야 함, 캐시)와 6장 앞까지 풀고 멈춤. 예전에는 `Ok(false)`가 블록 건너뛰기라 다음 블록으로 계속 진행해 비솔리드 압축파일은 페이지 하나에 책 전체를 풂. 풀기는 한 번에 하나(같은 블록을 작업자 4개가 동시에 처음부터 풀지 않음, 기다린 작업자는 캐시에서 찾음), 이미 캐시에 있는 페이지는 다시 복사하지 않음, 사용자가 떠난 페이지는 취소로 멈춤. 캐시(128 MiB)는 가득 차면 전부 비우지 않고 가장 오래 안 쓴 것부터
- 저장: 방향 적용은 행 단위 병렬 정수 재배치(f64 UV 계산 제거), 보정은 표 + 병렬, 단계마다 이전 버퍼를 바로 놓고 보정은 공유되지 않은 버퍼에 제자리로. 인코더용 변환(`prepare`)은 한 번에 만들고(RGBA 복사 후 RGB로 또 복사하던 것 제거), 내보내기는 디코드 픽셀을 인코더 변환 전에 놓음
- 디코더 복사: AVIF(8·16비트)·16비트 ICC 변환·image-rs 대체 경로(JPEG XL 포함)·16비트/부동소수 보정이 결과 버퍼 하나에 바로 씀(`ImageBuf::with_samples`), 중간 `Vec<[u8; 4]>`·`to_vec()` 복사 제거

## 7. 테스트 전략

- **코덱**: 형식별 샘플 코퍼스(`testdata/`), probe 결과·크기·프레임 수 검증, 손상 파일에서 패닉 없이 오류 반환
- **인코더 왕복**: `decode(encode(x))`와 `x` 비교 — 무손실은 완전 일치, 손실은 PSNR 하한
- **편집 연산**: 작은 합성 이미지에 대한 골든 픽셀 테스트, 연산 조합 교환 법칙(회전 4번 = 원본 등) 속성 테스트
- **내보내기**: 쓰기 도중 실패 주입 시 원본 무손상, 메타데이터 보존·방향 태그 재설정 확인
- **성능**: `iv bench` 결과를 단계별로 기록해 회귀 감시
- **동시성**: 빠른 연속 탐색 시뮬레이션 테스트에서 캐시 메모리 상한·누수 없음 확인

## 8. 열린 결정 사항

- 색 관리: `moxcms`(순수 Rust, C 빌드 불필요) vs `lcms2`(검증된 C 라이브러리) — M3에서 정확도·속도 측정 후 결정
- JPEG 디코더: `zune-jpeg` vs libjpeg-turbo — M0 벤치마크로 결정
- RAR 지원 여부: unRAR 라이선스 조건 검토 후 결정
- 런타임 플러그인 필요 여부: M5 이후 실제 수요로 판단

### 출시 전 점검: 빠진 기본 기능 (2026-11-17)

- 휴지통으로 옮기기(Delete, `file.delete`): `SHFileOperationW`(`FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_SILENT | FOF_WANTNUKEWARNING`). 묻기는 뷰어가 직접(설정 "휴지통으로 옮기기 전에 묻기", 기본 켬; 저장하지 않은 편집이 있으면 설정과 관계없이 묻음). 휴지통에 넣을 수 없는 파일(네트워크 드라이브 등)은 셸이 "영구 삭제" 경고를 띄움. 성공 판정은 반환값이 아니라 파일이 실제로 없어졌는지. 그 뒤 `FolderList::remove`로 목록에서 빼고 캐시를 비운 뒤 다음 이미지(마지막이었으면 새 마지막)를 보여 줌, 폴더가 비면 빈 창. 폴더 목록이 아직 안 왔으면 그 자리에서 폴더를 읽고 `index_after`로 다음 이미지를 찾음. 압축파일 안의 페이지·저장 중에는 하지 않음. 화면에 보이는 이미지가 지금 이미지일 때만(다음 이미지를 읽는 동안·지운 직후에는 이전 이미지가 화면에 남으므로 "아직 화면에 나오지 않아 옮기지 않음" 알림, 열 수 없는 파일은 제목에 오류가 보이므로 허용). 키를 누르고 있어도 한 번만(자동 반복 무시)
- 클립보드: 이미지 복사(Ctrl+C, `edit.copy_image`)는 화면 그대로(편집 적용, 애니메이션은 지금 프레임) `iv_ops::apply::render` → 24비트 `CF_DIB`(투명 부분은 흰색과 합성). 투명한 이미지는 알파가 있는 `CF_DIBV5`(sRGB, straight alpha)와 `PNG` 형식도 함께. 파일 복사(Ctrl+Alt+C, `file.copy_file`)는 `CF_HDROP` + `Preferred DropEffect = 복사`(탐색기에 붙여 넣으면 복사, 채팅에는 첨부), 경로 복사(Ctrl+Shift+C, `file.copy_path`)는 텍스트(압축파일 페이지는 뷰어가 여는 가상 경로). 바이트 만들기는 `iv_win::clipboard`(창 없이 테스트)
- 폴더에서 보기(Ctrl+Shift+E, `file.show_in_folder`): `SHOpenFolderAndSelectItems`로 탐색기에서 파일 선택(압축파일 페이지는 압축파일). `explorer /select,` 명령줄은 쉼표·공백 따옴표 문제로 쓰지 않음
- 아이콘·버전: 아이콘은 코드로 그림(`src/app_icon.rs`, 16~256 px 8가지, 8×8 슈퍼샘플링, PNG 이미지로 15 KB)이고 `res/app.ico`가 그 그림과 픽셀 단위로 같은지 테스트가 확인(`IV_WRITE_ICON=1`로 다시 씀). `build.rs`가 `res/winres.rs`로 아이콘 그룹 + `VERSIONINFO`(Cargo.toml 버전, FileDescription·ProductName 등)를 담은 `.res`를 직접 써서 링커에 넘김 → 탐색기·작업 표시줄·"연결 프로그램"·속성 > 자세히에 이름·버전·아이콘. 창 클래스는 `LoadImageW`로 큰·작은 아이콘을 시스템 크기에 맞게. 정보(Shift+F1, `app.about`): 버전·설정 폴더·기록 폴더·홈페이지(`CARGO_PKG_REPOSITORY`). `--version`(`-V`)은 두 실행 파일 모두, 콘솔 없는 릴리스 빌드는 실행한 콘솔에 붙어서 출력
- "연결 프로그램" 등록: 설정 창의 등록/등록 해제 버튼 또는 `--register`/`--unregister`. `HKEY_CURRENT_USER`만(관리자 권한 없음): `Software\Classes\Applications\image-viewer.exe`(FriendlyAppName, SupportedTypes, open 명령), ProgID `ImageViewer.Image`·`ImageViewer.Archive`(형식 이름, 아이콘, open 명령), 확장자마다 `.<ext>\OpenWithProgids`, `Software\image-viewer\Capabilities` + `RegisteredApplications`(기본 앱 목록). 확장자 목록은 코덱 레지스트리(`FormatId`)와 압축파일 읽기에서. 해제는 등록한 것만 지움: 뷰어 전용 키는 통째로, 다른 프로그램과 함께 쓰는 키(`.jpg\OpenWithProgids` 등)는 뷰어 값만 지우고 비었을 때만 키 삭제. `UserChoice`(사용자가 고른 기본 앱)는 건드리지 않음 — Windows 10/11에서는 프로그램이 스스로 기본 앱이 될 수 없으므로 "기본 앱 설정…" 버튼으로 설정 > 기본 앱을 엶. 쓸 값·지울 값 계획은 `iv_win::assoc`(플랫폼 독립 테스트), 실제 레지스트리 왕복은 `HKCU\Software\image-viewer-test-*` 임시 키에서 테스트

### 출시 준비: 배포 패키지 (2026-11-17)

- C 런타임 정적 링크: `.cargo/config.toml`의 `[target.x86_64-pc-windows-msvc] rustflags = ["-C", "target-feature=+crt-static"]`. 로컬·CI·배포 빌드가 모두 같은 플래그를 쓰므로 유닛 지문이 하나뿐(환경 변수 `RUSTFLAGS`는 이 설정을 대체하므로 쓰지 않음). `cc`로 빌드하는 libwebp도 `/MT`를 따름. 결과: 두 실행 파일의 가져오기에서 `VCRUNTIME140.dll`과 `api-ms-win-crt-*` 7개가 사라짐(UCRT도 정적), 크기는 각각 약 170 KB 증가(image-viewer 18.60 → 18.77 MB). `tests/executable.rs`가 디버그 실행 파일의 가져오기 표를 직접 읽어 확인

### 업데이트 확인과 "연결 프로그램" 경로 고침 (2026-11-18)

배포는 휴대용 zip(`image-viewer.exe` + `iv.exe`)이고 설정은 `%APPDATA%\image-viewer`에 있으므로, 업그레이드는 exe를 덮어쓰거나 다른 폴더에 푸는 것(README "업그레이드"). 문제는 두 가지였음: 새 버전이 나왔는지 알 길이 없고, "연결 프로그램" 등록(`HKCU`)이 exe 경로를 기억해 다른 폴더에 풀고 예전 폴더를 지우면 없는 exe를 가리킴.

- 저장소 주소는 한 곳: 루트 `Cargo.toml`의 `[workspace.package] repository`(멤버는 `repository.workspace = true`). 코드의 모든 주소는 `env!("CARGO_PKG_REPOSITORY")`(`update::REPOSITORY`)에서 만듦: API `https://api.github.com/repos/<소유자>/<저장소>/releases/latest`(`update::latest_release_api`, github.com 주소가 아니면 `None`), 릴리스 목록 `<저장소>/releases`, 정보 창의 홈페이지
- 확인(`update.rs`, 플랫폼 독립): `evaluate(상태, 본문, 현재 버전, 저장소)` → `Outcome::{UpToDate, Newer{latest, page}}` 또는 `Failure::{Offline, Timeout, Tls, Network(코드), RateLimited(403·429), Http(상태), TooLarge, Unreadable, NotStarted(확인 스레드를 만들지 못함)}`. 버전 비교는 유의적 버전 규칙(`v` 접두어, 빠진 minor·patch는 0, pre-release는 그 릴리스보다 아래이고 점으로 나눈 부분을 숫자·문자 규칙으로, `+build`는 형식만 검사하고 비교에서는 무시). 태그는 그대로 상태 줄에 나오므로 엄격하게: 식별자는 `[0-9A-Za-z-]`만(`+build` 포함), 숫자 앞 0 금지, 앞뒤 공백·제어 문자 금지, 64바이트(`MAX_TAG`)까지. JSON은 serde_json 대신 최상위 객체의 `tag_name`·`html_url` 두 문자열만 읽는 작은 파서(엄격: 유효한 UTF-8, 하나의 완전한 객체, 중첩 64단계까지, 이스케이프·서로게이트 쌍 검사, 두 필드 중복이면 거부). 열 페이지는 `html_url`이 `<저장소>/releases/`로 시작하고 평범한 URL 문자만(`..`도 `%`도 없이 — `%2e%2e`로 다른 경로로 가지 못하게) 있을 때만 그것, 아니면 릴리스 목록
- 요청(`win/update_check.rs`): WinHTTP(`Win32_Networking_WinHttp` 기능, 새 HTTP·TLS 크레이트 없음). `WINHTTP_ACCESS_TYPE_AUTOMATIC_PROXY`(지원하지 않는 Windows면 `DEFAULT_PROXY`), 헤더는 User-Agent `image-viewer/<버전>`과 `Accept: application/vnd.github+json`만, 쿠키 끔, 자동 로그온 정책 HIGH(Windows 자격 증명을 보내지 않음), TLS 1.2/1.3. 시간 제한은 단계마다 10초(`WinHttpSetTimeouts` + `WINHTTP_OPTION_RECEIVE_RESPONSE_TIMEOUT`)와 본문 읽기 전체 10초 — 본문 제한은 헤더가 온 때부터 재고(프록시 찾기·연결·헤더가 합쳐 10초를 넘어도 답을 버리지 않음), 읽을 때마다 확인. 동기 `WinHttpReadData`는 버퍼가 찰 때까지 기다리므로 먼저 `WinHttpQueryDataAvailable`로 와 있는 만큼만 읽음(그래야 조금씩 흘려 보내는 서버에서 제한이 지켜짐). 실측: WinHTTP는 시간 제한을 약 4초 단위로 올려 확인함(0.5~3초 → 4초, 6초 → 8초, 10초 → 12.0초). 응답은 1 MiB까지(`Content-Length`로 먼저, 읽으면서 다시). `Endpoint`의 평문 HTTP는 이 컴퓨터(`127.0.0.1`·`localhost`·`::1`)에만 허용되고(그때는 프록시 없음) 그 밖은 생성자가 거부 — 테스트가 이 경로로 진짜 WinHTTP 코드를 돌림. 오류 코드 → 이유: 12002 시간 초과, 12007·12029 연결 없음, 12175·12188 보안 연결, 12152 알아볼 수 없음
- 앱: 설정 창의 버튼 → `UiEvent::CheckUpdate` → 확인 중이 아니면 `update-check` 스레드 → `AppEvent::UpdateChecked` → `settings_window::set_update`. 확인 중에는 버튼을 끄고(포커스가 있었으면 탭 줄로), 새 버전일 때만 "릴리스 페이지 열기"(`open_uri`). 설정 창은 닫아도 숨기기만 하므로 결과가 와도 안전하고, 뷰어를 먼저 닫으면 받는 쪽이 없어 결과를 버린 채 프로세스와 함께 끝남. 상태는 설정 창이 들고 있어 언어를 바꾸면 다시 씀. 자동·주기 확인 없음
- `--check-update`: 창 없이 같은 확인을 하고 상태 줄과 같은 문장(설정 언어)을 콘솔에 씀, 새 버전이면 다음 줄에 페이지 주소. 실패면 종료 코드 1
- WinHTTP는 지연 로드(`/DELAYLOAD:winhttp.dll` + `delayimp.lib`, `iv-win/build.rs`의 bin 링크 인자): 시작할 때 매핑하면 창 생성 전에 약 1 ms가 늘었음(HEAD 대비 window created 16.1 → 17.0 ms). `tests/executable.rs`가 winhttp.dll이 가져오기 표가 아니라 지연 로드 표에만 있는지 확인
- 등록 경로(`assoc.rs`, 플랫폼 독립): 등록이 가리키는 exe는 `ImageViewer.Image\shell\open\command`의 명령에서 읽음(`command_exe`: 따옴표 있는/없는 명령). `look_up(등록된 exe, 현재 exe)` → `Found::{Present, SameFile, Gone, Unknown}`: `Gone`은 `metadata`가 NotFound이고 그 경로의 루트(`C:\`, `\\서버\공유\`, `volume_root`)를 읽을 수 있을 때만 — 빠진 드라이브 문자·연결되지 않은 공유도 NotFound(ERROR_PATH_NOT_FOUND)를 내므로 루트를 따로 봄. 그 밖의 오류(권한 없음, 준비 안 된 드라이브)는 `Unknown`. 파일이 있으면 둘 다 `canonicalize`해서 같으면 `SameFile`(subst 드라이브·정션·8.3 이름). `check(등록된 경로, 현재 exe, Found)` → `NotRegistered` / `Here`(대소문자·슬래시·`\?\` 무시하고 같은 경로, 또는 `SameFile`) / `Repair{old}`(`Gone`일 때만) / `OtherCopy(경로)`(있는 다른 exe, 또는 `Unknown`)
- 시작할 때(`window.rs`, 창을 띄운 뒤): `open-with-check` 스레드가 `shell::repair_registration("", 현재 exe, 언어)`(`--settings`로 따로 설정 파일을 준 실행은 고치지 않고 보기만: 시험 실행·두 번째 사본이 사용자의 실제 등록을 `target\` 빌드 쪽으로 옮기지 않게) — `Repair`면 쓰기 잠금(`shell::writing`, 등록/해제 버튼도 같은 잠금)을 잡고 등록이 그사이 바뀌지 않았는지 다시 읽은 뒤(바뀌었으면 그 선택을 그대로 둠) `assoc::registration(현재 exe)` 값을 그대로 다시 쓰고, 예전 exe 이름이 달랐으면 그 `Applications\<예전 이름>` 키를 그 명령이 예전 exe를 가리킬 때만 지운 뒤 `SHChangeNotify`. `OtherCopy`·`NotRegistered`는 아무것도 쓰지 않음. 결과는 `AppEvent::Registration`으로 와서 제목 표시줄 알림(고쳤을 때)과 설정 창의 줄("등록됨: 이 실행 파일" / "다른 사본에 등록됨: 경로" / "없는 파일에 등록됨: 경로" / "등록되지 않음", `SS_PATHELLIPSIS`·`SS_NOPREFIX`). 설정 창을 열 때와 등록/해제 뒤에도 같은 스레드로 다시 봄(고치지는 않음). 확인은 한 번에 하나: 하나가 도는 중에 또 요청하면 끝난 뒤 한 번 더 보고, 그사이의 (바뀌기 전에 읽었을 수 있는) 결과는 줄에 쓰지 않음 — 느린 드라이브에서 고치기가 늦게 끝나도 "없는 파일에 등록됨"이 남지 않음. 등록된 exe가 느린·빠진 드라이브에 있을 수 있어 파일 확인은 UI 스레드에서 하지 않음
- 설정 창 일반 탭: 등록 버튼 아래 등록 줄, 버전, 업데이트 줄(버튼 두 개 + 상태 줄, `SS_ENDELLIPSIS`). 창 높이 368 → 384. 줄 사이 간격은 컴파일 시 검사(`REGISTRATION_Y`·`VERSION_Y`·`UPDATE_Y`·`BUTTONS_Y`)
